# aiagent

Автор: **Кислов Роман Сергеевич**. Лицензия: [Apache 2.0](LICENSE). Рабочий интерфейс и CLI сохраняют название Superagent.

Основной репозиторий поддерживает @rkislov; предложения — через issues и PR, см. [CONTRIBUTING.md](CONTRIBUTING.md).

Локальная Python-платформа для сборки агентов из навыков. FastAPI, React, CodeMirror, SQLite. Пользовательские пространства с паролем и TOTP-2FA, без Docker.

## Запуск

Нужен Python 3.11+. Команды выполняются из корня этого проекта:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -e '.[test]'
python -m platform serve
```

Откройте [localhost:8080](http://localhost:8080). Собранный фронтенд включён в репозиторий; Node.js нужен только для его изменения.

Готовый `office_assistant` использует **demo:office**: это детерминированная демонстрация, а не языковая модель. Нажмите «Разобрать входящие», чтобы проверить цепочку `email_filter → report_gen`, или «Сохранить результат», чтобы проверить подтверждение записи файла. Демо не подключается к настоящей почте. Оно принимает JSON с массивом `messages` либо обычный текст, который трактуется как одно письмо.

## CLI

```bash
python -m platform skills list
python -m platform skills validate email_filter
python -m platform skills test email_filter --input '{"messages":[{"subject":"Счёт на оплату","body":"Срочно"}]}'
python -m platform agents build office_assistant
python -m platform agents chat office_assistant
python -m platform agents run office_assistant --message 'Разбери письмо: хочу купить продукт'
python -m platform agents chat office_assistant --session my_conversation
python -m platform serve --port 8081
```

`/exit` завершает диалог. Подтверждение в CLI принимается только при вводе `y`; пустой ввод и EOF означают отказ.

Основной пакет называется `superagent`, чтобы не перекрывать стандартный модуль Python `platform`. Репозиторная оболочка сохраняет команды из ТЗ и экспортирует стандартные функции `platform.system()` и другие. При установке пакет `platform` не распространяется. Из других каталогов используйте:

```bash
superagent --root /absolute/path/to/superagent serve
# или
python -m superagent --root /absolute/path/to/superagent skills list
```

Путь можно также задать переменной `SUPERAGENT_HOME`.

## Настройка моделей

Скопируйте `config.example.yaml` в `config.yaml`. Укажите доступные вам модели, затем выберите модель в конструкторе агента. Ключи предпочтительно передавать через переменные окружения:

```bash
export OPENAI_API_KEY='...'
export ANTHROPIC_API_KEY='...'
```

Провайдер определяется частью строки до первого двоеточия: `openai:gpt-4o-mini`, `ollama:qwen3:8b`, `anthropic:ваш-model-id`. Имена моделей в примере нужно согласовать с доступом вашей учётной записи и установленными моделями Ollama. Для OpenAI-совместимого сервера добавьте провайдер с `type: openai`, собственным `base_url` с `/v1` и списком моделей. `api_key_env: null` подходит для локального сервера без авторизации. Допускается `api_key` в приватном `config.yaml`; он исключён из git.

Ответы передаются от провайдера потоково: OpenAI и Anthropic через SSE, Ollama через NDJSON. Веб-клиент получает SSE через `POST /api/chat`. Использованные протоколы: [OpenAI Chat Completions](https://developers.openai.com/api/reference/resources/chat), [Anthropic Messages](https://platform.claude.com/docs/en/api/messages), [Ollama Chat](https://docs.ollama.com/api/chat).

## Навыки и агенты

Навык находится в `skills/<name>/`. `SKILL.md` содержит YAML front matter и необязательное описание после него. `skill.py` определяет синхронную функцию `run(input: dict) -> dict`. При сканировании код разбирается через AST, но не исполняется.

```yaml
---
name: uppercase
description: Переводит текст в верхний регистр
version: 0.1.0
inputs:
  text: str
outputs:
  result: str
permissions:
  filesystem: []
  network: []
  subprocess: false
irreversible: false
---
```

```python
def run(input: dict) -> dict:
    return {"result": input["text"].upper()}
```

Поддерживаемые типы: `str`, `int`, `float`, `bool`, `dict`, `list`, `any`, `list[T]`, включая `list[dict]`. Объявленные поля обязательны; лишние поля входа и выхода отклоняются. Имена: `[a-z][a-z0-9_]{0,63}`. Для операций с внешним эффектом указывайте `irreversible: true`. Поле `confirmation_required` агента содержит имена прикреплённых навыков.

Файлы агентов находятся в `agents/*.yaml`; пример — `agents/office_assistant.yaml`. Конструктор проверяет наличие навыков, провайдера, путь памяти, права и несовместимые типы одноимённых полей между навыками. Он не строит статический граф бизнес-процесса: последовательность независимых инструментов выбирает модель. Сохранения из UI регистрируются без перезапуска, `GET /api/workspace` также пересканирует файлы.

## Песочница и подтверждения

Изоляция ОС обязательна. При отсутствии поддерживаемого механизма платформа отказывает в исполнении:

- **macOS:** встроенный `/usr/bin/sandbox-exec`, профиль `deny default`. Проверено на этой машине.
- **Linux:** `bubblewrap` (`bwrap`) с отдельными namespaces и `libseccomp.so.2` для запрета fork/exec при `subprocess: false`. Например, на Debian/Ubuntu: `sudo apt install bubblewrap libseccomp2`. В системе должны быть доступны непривилегированные user namespaces. Linux-бэкенд включён, но в этой сессии на Linux не проверялся.
- **Windows:** нативный бэкенд отсутствует; используйте Linux/WSL с указанными зависимостями.

Рабочий процесс получает только JSON запроса, копию кода и минимальное окружение без API-ключей, `HOME` и `PYTHONPATH`. Запуск с `-I -S -B` отключает пользовательские и установленные site-packages. По умолчанию доступны стандартная библиотека и системные библиотеки интерпретатора только для чтения; произвольные пользовательские файлы, IP-сеть и подпроцессы запрещены. Python audit hooks дополняют ограничения ОС понятными сообщениями.

`permissions.filesystem` — явные пути для чтения и записи; относительные пути разрешаются от корня проекта. Корень, домашний каталог, исходники платформы, агенты, навыки, конфигурация и внутренние файлы `data/` защищены от выдачи навыкам. Внутри `data/` разрешается только `data/workspace/`. Каталог должен существовать. Модуль `skill_context` предоставляет `filesystem` — кортеж абсолютных разрешённых путей и `network` — разрешённые пары IP/порт. Пример `save_report` использует этот контекст.

Для сети адреса `host:port` разрешаются до запуска. Родительский процесс создаёт Unix-сокет с фиксированным TCP-адресатом для каждого разрешённого IP/порта. Политика ОС допускает только эти сокеты; сырая IP-сеть ребёнка закрыта. Обычные `socket.socket.connect`, `socket.create_connection`, а также использующие их stdlib-клиенты проходят через эти relay-сокеты. DNS ребёнка закреплён за разрешёнными адресами, UDP не поддерживается. Нативные клиенты, не использующие Python `socket`, не имеют прямого сетевого доступа. У каждого запуска максимум 16 одновременных relay-соединений.

Подтверждение обязательно для навыков с `irreversible: true`, перечисленных агентом действий, а также любых навыков с файловыми, сетевыми или subprocess-правами. Отсутствие ответа, таймаут, отказ и отключение чата не разрешают действие. Одно подтверждение привязано к одному вызову. В начале запуска фиксируются метаданные и код навыков, поэтому сохранение редактора не меняет уже ожидающее подтверждения действие. Тестирование навыка из редактора также запрашивает разрешение на расширенные права.

По умолчанию время навыка — 60 секунд, модели — 120 секунд, подтверждения — 300 секунд, лимит цикла — 10 шагов. На один чат допускается только один активный запуск. Отмена чата запрещает последующие вызовы; уже запущенный синхронный вызов может завершиться до своего таймаута. Потомки навыка завершаются вместе с его process group. Ресурсные лимиты ограничивают CPU, размер файлов и число дескрипторов, а на Linux также адресное пространство.

## Хранение и веб-API

- `data/memory.db`: сессии и полная история сообщений. Модели передаются последние `context_turns` завершённых диалоговых ходов (по умолчанию 20), с целыми группами вызовов инструментов.
- `data/audit.log`: JSON Lines, ротация по размеру и числу копий из конфига.
- `data/audit.db`: постоянный индекс событий для фильтров UI и пагинации. Ротация JSONL не удаляет историю SQLite.
- `data/workspace/report.txt`: файл демонстрационного действия после подтверждения.

Аудит содержит время UTC, агента, сессию, тип события, навык, вход, выход, статус и длительность. Из записей удаляются известные ключи провайдеров и значения полей с именами `api_key`, `password`, `authorization`, `secret`, `token`. Содержимое диалогов хранится локально без шифрования.

Основные маршруты описаны в [OpenAPI](http://localhost:8080/docs): `/api/workspace`, `/api/agents/{name}`, `/api/agents/{name}/build`, `/api/skills/{name}`, `/api/skills/test`, `/api/chat`, `/api/confirmations/{id}`, `/api/sessions/{agent}`, `/api/audit`.

Сервер привязан к `127.0.0.1`. Host allowlist и проверка Origin отклоняют DNS rebinding и запросы с других сайтов; изменяющие запросы принимают только JSON. Текущая версия включает вход и изоляцию пользователей; для публикации требуется HTTPS.

## Разработка и проверка

```bash
pytest -q

npm ci
npm run build
```

В тестах проверяются реальное исполнение песочницы, запреты файлов/сети/подпроцессов, очистка окружения, разрешённые операции, таймаут, схемы, реестр, лимит шагов, подтверждения и фиксация кода, память, ротация/редакция аудита, протоколы провайдеров, CRUD API и живое SSE-подтверждение через HTTP. Для внешних моделей используются поддельные HTTP-ответы: платные API и локальные модели не вызываются.

Архитектура:

```text
superagent/

  core/           цикл агента, память и провайдеры
  sandbox/        OS-политика, отдельный worker и сетевые relay

platform/         совместимость команды из ТЗ
skills/           три демонстрационных навыка

tests/            автоматические проверки
```

## Границы MVP

Не включены Docker-бэкенд, автоматическая установка `requirements.txt` навыков, сторонние Python-зависимости внутри worker и RAG. Подключения и многопользовательский режим описаны ниже. Навыки MVP используют стандартную библиотеку. Подключение внешних моделей реализовано, но с реальными ключами в этой сессии не проверялось. ОС-песочница снижает возможности навыка; она не является обещанием безопасности произвольного враждебного нативного кода или уязвимого ядра.

## Обновление: подключения, модели навыков и пользователи

Веб-интерфейс теперь требует входа. При первом открытии создайте администратора (логин латиницей, пароль от 12 символов), добавьте показанный TOTP-секрет в приложение-аутентификатор и подтвердите шестизначным кодом. Для последующих входов нужны пароль и новый код. Хеши паролей — Argon2; сессии — случайные HttpOnly/SameSite cookies со сроком 12 часов. Повторное использование TOTP-кода отклоняется, попытки ограничены. При удалённом размещении необходим HTTPS для Secure cookies.

Администратор создаёт пользователей через «Подключения». Каждый новый пользователь начинает с пустыми агентами и собственными встроенными подключениями. Старый однопользовательский каталог не копируется другим пользователям. Пространства находятся в `data/users/<id>/`; раздельно хранятся YAML агентов, пользовательские навыки, настройки, секреты, SQLite-память и аудит. Python-навыкам веб-пользователей разрешён доступ только к собственному `data/workspace`. Общие переменные окружения сервера для пользовательских ключей не используются. Эта изоляция относится к приложению и навыкам; администратор ОС с доступом к файлам сервера остаётся доверенным.

Раздел «Подключения» позволяет добавлять провайдеров, ключи и список моделей, сохранять настройки и выполнять тестовый запрос к модели. Пустое поле существующего секрета сохраняет его значение. Ключи хранятся в пользовательском `config.yaml` с правами 0600 и не возвращаются в браузер. Список моделей задаётся JSON-массивом, например `["model-one", "model-two"]`.

В конструкторе агента для каждого прикреплённого навыка можно назначить отдельную модель обработки результата (`skill_models: {rss_read: "ollama:qwen3:8b"}`). Сам навык получает данные, назначенная модель анализирует их, основная модель агента формирует итоговый ответ. Пустое назначение означает отсутствие дополнительного модельного вызова. Вызовы дополнительных моделей также аудируются.

Встроенные навыки (настраиваются через подключения, не перезаписываются Python-кодом):

- `web_search`: Tavily, Brave или SearXNG. Для Tavily адрес `https://api.tavily.com`, Brave — `https://api.search.brave.com`, SearXNG — адрес вашего экземпляра с разрешённым JSON API. Вход: `{"query":"новости Python","limit":5}`.
- `imap_read`: TLS на 993 или STARTTLS на 143; логин и пароль приложения, список разрешённых папок. Использует readonly SELECT и BODY.PEEK, не помечает письма прочитанными. Вход: `{"folder":"INBOX","query":"UNSEEN","limit":5}`.
- `caldav_read`: URL CalDAV, логин и пароль приложения; необязательный список имён/URL календарей. Только чтение, интервал до 93 дней. Вход: `{"start":"2026-11-21T00:00:00+03:00","end":"2026-11-28T00:00:00+03:00","calendar":"","limit":20}`.
- `rss_read`: RSS/Atom, список `feeds` в формате `[{"name":"news","url":"https://example.org/feed.xml"}]`. Вход: `{"feed":"news","limit":10}`; пустое имя читает все настроенные ленты. URL может задавать только пользователь через настройки, не модель; размер ленты ограничен 2 MB, редиректы не выполняются.

Встроенные подключения — доверенные адаптеры платформы с собственными учётными данными, а не произвольный код в песочнице. Их вызовы агентом требуют подтверждения. Проверка из раздела настроек читает реальные данные по явному нажатию пользователя. Внешние учётные записи без заданных пользователем реквизитов не подключены.

### Каналы общения

В разделе подключений добавьте Telegram, Mattermost или XMPP, задайте агента и непустой allowlist. Запускайте worker отдельно для нужного пользовательского пространства:

```bash
python -m superagent --root /absolute/project/data/users/USER_ID channels run telegram
```

Для Telegram нужен bot token, `allowed` содержит строковые ID разрешённых чатов; используется long polling без публичного webhook. Для Mattermost нужны URL сервера и bot token, `allowed` содержит ID каналов; worker опрашивает новые сообщения и отвечает в треде. Для XMPP задайте JID бота и пароль, `allowed` содержит bare JID собеседников; используется slixmpp. Каналы не запускаются автоматически при сохранении настроек. Действия, требующие подтверждения, в этих каналах отклоняются. Обработчики рассчитаны на локальный запуск; автоматический reconnect/supervisor и гарантированная доставка после перезапуска пока отсутствуют.

Установите новые зависимости: `pip install -e '.[test]'`. После обновления перезапустите сервер. Проверки интеграций используют поддельные HTTP/IMAP-ответы; проверка внешних серверов и мессенджеров требует ваших реквизитов.

### QR-код 2FA и восстановление доступа

При первом входе экран настройки показывает QR-код для TOTP-приложения. QR генерируется локально; секрет не передаётся сторонним сервисам. Ручной ввод секрета доступен в раскрывающемся блоке.

После подтверждения настройки показываются 10 резервных кодов. Скачайте их и сохраните отдельно от устройства с аутентификатором: повторно посмотреть значения нельзя. Уже существующие пользователи получат первый набор при следующем успешном входе с TOTP.

Если приложение-аутентификатор недоступно, после ввода логина и пароля выберите «Нет доступа к приложению? Резервный код». Один резервный код заменяет второй фактор только один раз; пароль по-прежнему обязателен. Резервный код не отключает 2FA. В базе сохраняются только хеши кодов; использование отмечается атомарно, включая одновременные попытки входа.

Кнопка «Резервные коды» после входа позволяет перевыпустить весь набор. Потребуется повторно подтвердить пароль и свежий TOTP либо неиспользованный резервный код. После перевыпуска все старые коды перестают работать. Ответы авторизации и восстановления имеют `Cache-Control: no-store`.

### Смена пароля и административный сброс 2FA

В верхней панели доступна «Сменить пароль»: текущий пароль, новый пароль от 12 символов и свежий TOTP либо неиспользованный резервный код. После смены завершаются все сессии и незавершённые запросы входа; нужно войти заново. Сам секрет 2FA и остальные резервные коды сохраняются.

Администратору доступна «Сбросить 2FA пользователя». Он указывает логин пользователя и подтверждает **свои** пароль и второй фактор. Сброс удаляет сессии, запросы входа и резервные коды указанного пользователя, заменяет TOTP-секрет и требует повторного подключения аутентификатора при следующем входе с прежним паролем. Самосброс через этот механизм запрещён. Контент пользователя сохраняется. Операции фиксируются без секретов в таблице `security_events` базы `data/auth.db`.

### Новые навыки

- `morning_digest`: агрегирует включённые IMAP, CalDAV и RSS в структурированную сводку. Вход: start/end с часовым поясом и limit.
- `meeting_prep`: собирает события за интервал и последние письма для подготовки к встречам; связывание по смыслу делает модель агента. Вход: start/end/limit.
- `topic_monitor`: ищет query в настроенном поиске и отбирает совпадения из RSS, limit до 20.
- `commitment_scan`: извлекает предложения с признаками обещаний и явные даты из text. Это кандидаты для проверки, а не гарантированное распознавание обязательств.
- `invoice_check`: принимает invoices с полями vendor, number, amount, currency, due_date (ISO), paid. Ищет возможные дубли по поставщику/номеру/валюте, некорректные суммы и просрочки. Не оплачивает счета.
- `reply_drafts`: возвращает шаблонные черновики по messages, без отправки. Для содержательного ответа назначьте навыку модель обработки результата.

### SSH

Подключение `ssh` содержит host, port, username, password, host_key_sha256 и commands — JSON-массив **точных** разрешённых команд. Отпечаток `SHA256:…` получите и проверьте вне агента через доверенный канал. Агент не принимает неизвестный ключ автоматически и не использует SSH-agent или чужие локальные приватные ключи. В этой версии поддерживается парольная аутентификация.

Навык `ssh_run` получает `{"command":"uptime"}` и требует явного подтверждения каждого вызова. Вывод ограничен 128 KB, время ожидания команды — 30 секунд; при таймауте удалённая команда могла продолжить выполнение. Проверка SSH через общий тестовый endpoint запрещена: используйте агента с подтверждением. Не добавляйте в allowlist команду, последствия которой вы не готовы разрешить.

### Бухгалтер 1С через OData

В разделе «Агенты» нажмите «Создать бухгалтера 1С (OData)», выберите подключённую модель и сохраните агента. Репозиторный пример: `agents/accountant_1c.yaml`. Пространства пользователей не получают чужие файлы: кнопка создаёт собственный экземпляр.

В `one_c` настройте URL вида `https://server/base/odata/standard.odata`, логин, пароль и entities — список разрешённых имён коллекций из метаданных вашей базы. Навык `one_c_read` выполняет только GET с `$format=json`, `$top`, необязательными `$filter` и `$select`. Он не записывает и не проводит документы. Вход: `{"entity":"ИМЯ_ИЗ_МЕТАДАННЫХ","filter":"","select":"","limit":20}`. Ответ ограничен 2 MB. Конкретные поля вашей конфигурации нужно сопоставить с полями проверки счетов; готовой универсальной схемы для всех конфигураций 1С нет.

Протоколы: [стандартный REST/OData-интерфейс 1С](https://1c-dn.com/1c_enterprise/rest_interface/?type=original), [SSH-клиент Paramiko](https://docs.paramiko.org/en/stable/api/client.html). Реальные 1С и SSH-серверы без предоставленных реквизитов не проверялись; тесты используют поддельные ответы.

### Быстрое подключение OpenAI (ChatGPT) и DeepSeek

В разделе «Подключения» используйте кнопки «Настроить/Добавить ChatGPT / OpenAI API» и «Настроить/Добавить DeepSeek API». Они открывают существующую карточку без изменения её ключа либо добавляют готовый шаблон с адресом API и моделями. Вставьте свой API-ключ, выберите модель для теста и нажмите «Сохранить и проверить модель». Затем выберите `openai:…` или `deepseek:…` в конструкторе агента или в модели обработки отдельного навыка.

OpenAI использует `https://api.openai.com/v1`, DeepSeek — `https://api.deepseek.com`. Оба подключения поддерживают потоковые ответы и инструменты. Для официального DeepSeek API используется `thinking: disabled`, чтобы цикл навыков работал без переноса дополнительных данных рассуждения. Список моделей редактируется пользователем, доступность проверяется его API-ключом. Ключи сервисов хранятся раздельно внутри пространства пользователя.

Источники для шаблонов: [модели OpenAI](https://developers.openai.com/api/docs/models), [DeepSeek API](https://api-docs.deepseek.com/), [режимы DeepSeek](https://api-docs.deepseek.com/guides/thinking_mode/). Проверки протокола автоматизированы на mock-ответах; платные реальные запросы без пользовательских ключей не выполнялись.

### Автоматическая загрузка моделей

После ввода API-ключа OpenAI или DeepSeek карточка автоматически запрашивает список моделей через backend спустя 800 мс без изменений поля. Ключ не сохраняется автоматически и не включается в ответ. Успешно загруженный список моделей автоматически сохраняется и сразу доступен в конструкторе агентов; нажимать «Сохранить настройки» для списка не нужно. Кнопка «Обновить список моделей» позволяет повторить запрос с сохранённым ключом.

Изменение ключа или адреса отменяет применение предыдущего запроса. При ошибке, пустом или некорректном ответе прежний список остаётся без изменений. Сохранённый ключ используется только для того же адреса API и текущего пользователя. Автозагрузка работает с официальными HTTPS-адресами OpenAI и DeepSeek, без переходов по редиректам. Список API может включать специализированные модели без поддержки Chat Completions/инструментов; их совместимость проверяется отдельным тестовым запросом.

Документация: [OpenAI List models](https://developers.openai.com/api/reference/resources/models/methods/list), [DeepSeek Lists Models](https://api-docs.deepseek.com/api/list-models/).

Автосохранение списка использует одноразовый запрос, привязанный к пользователю, провайдеру и состоянию его сохранённых настроек. Устаревшие результаты и результаты для изменившихся реквизитов отклоняются. Другие поля открытой формы, включая новый ключ, не сохраняются вместе со списком. Для нового провайдера создаётся только запись с адресом API и моделями без ключа; ключ сохраняется отдельно кнопкой настроек. Если меняется адрес уже сохранённого провайдера, сначала сохраните новое подключение, затем обновите модели.

## CLI: локальное администрирование и рабочие пространства

Все команды доступны как `superagent`, `python -m superagent` и из репозитория `python -m platform`. Справка: `superagent --help`, `superagent auth --help`, `superagent models --help`.

### Восстановление администратора

Выполните из обычного интерактивного терминала, находясь в корне проекта:

```bash
source .venv/bin/activate
python -m platform users list
python -m platform auth reset-admin ИМЯ_АДМИНИСТРАТОРА
```

Введите логин для подтверждения, затем новый пароль дважды. Ввод пароля скрыт, пароль не передаётся через аргументы, окружение, историю команд или журнал. Команда требует владения каталогом сервера и базой пользователей; запись для группы/других пользователей запрещена, база должна быть приватной. Работа через pipe без TTY отклоняется. Это аварийный локальный доступ владельца сервера, а не пользовательский веб-API; старый пароль и второй фактор при нём не требуются.

Пароль хранится как Argon2-хеш. Все сессии и незавершённые запросы входа администратора удаляются, ограничения неудачных попыток сбрасываются, контент сохраняется. Открытые веб-запуски обнаруживают отзыв сессии при следующей проверке и прекращают дальнейшие действия. Уже начатая внешняя команда не может быть отменена задним числом.

По умолчанию 2FA и оставшиеся резервные коды сохраняются. Если потерян также второй фактор:

```bash
python -m platform auth reset-admin ИМЯ_АДМИНИСТРАТОРА --reset-2fa
```

После этого при следующем входе понадобится настроить новый аутентификатор. Для отдельного аварийного сброса только 2FA: `auth reset-2fa ЛОГИН`. Восстановление записывается в `security_events` с UID локального оператора, без паролей и секретов. Обычного пользователя нельзя выбрать целью `reset-admin`.

### Основные команды

```bash
# Состояние, пользователи и первичная настройка
superagent status
superagent auth init admin
superagent users list
superagent users create alice

# Агенты и навыки
superagent agents list
superagent agents show office_assistant
superagent agents create /absolute/path/agent.yaml
superagent agents build office_assistant
superagent agents chat office_assistant
superagent agents run office_assistant --message 'Подготовь отчёт'
superagent skills list
superagent skills show web_search
superagent skills validate email_filter
superagent skills test email_filter --input '{"messages":[]}'

# Подключения и модели
superagent config show
superagent config import /absolute/path/config.yaml
superagent models list
superagent models set-key openai
superagent models refresh openai
superagent models test openai:gpt-4o-mini
superagent channels list
superagent channels run telegram

# История и аудит
superagent sessions list office_assistant
superagent sessions history office_assistant SESSION_ID
superagent audit --agent office_assistant --status error --limit 50

# Локальный сервер
superagent serve --port 8080
```

`auth init` применяется только к пустой базе. Пользователям CLI также нужен QR/TOTP при первом веб-входе. Пароли пользователей и API-ключи `models set-key` вводятся без эха через терминал. `config show` и `channels list` показывают признаки наличия секретов, а не их значения. В `config import` передаётся путь к приватному файлу; содержимое при ошибке не выводится. `models refresh` загружает и сохраняет список, не выводя ключ.

### Пространство конкретного пользователя

CLI — инструмент локального оператора сервера. Он выбирает пользовательское пространство явно, по логину:

```bash
superagent --root /absolute/path/to/superagent --user alice agents list
superagent --root /absolute/path/to/superagent --user alice models set-key deepseek
superagent --root /absolute/path/to/superagent --user alice audit --limit 20
```

Без `--user` команды работают с исходным однопользовательским каталогом корня проекта, а не с данными вошедшего в браузере пользователя. Административные `auth`/`users` и `serve` выполняются от корня сервера. Неизвестный логин не создаётся автоматически. После изменения конфигурации через CLI перезапустите веб-сервер, чтобы его уже открытые пользовательские пространства перечитали настройки; сброс пароля и отзыв сессий действуют сразу через общую БД.

## Jira, Confluence, Redmine и Bitrix24

В разделе «Подключения» появились отдельные карточки `jira`, `confluence`, `redmine`, `bitrix24`. Включите нужную карточку, задайте адрес и учётные данные, сохраните настройки. Реквизиты каждого пользователя изолированы; значения паролей/токенов не возвращаются в браузер. Для передачи логина и пароля используйте HTTPS. Права на данные определяются учётной записью внешнего сервиса; эти подключения не используют общую административную учётную запись платформы.

### Jira

`url`: адрес вашего сайта/сервера Jira, включая context path при наличии. `edition`: `cloud` или `server` (Server/Data Center). `auth_mode`: `basic` для логина/email + пароля/API-токена либо `bearer` для совместимого персонального токена. Учётные данные задаются в `username` и `password`. Использование API-токенов зависит от политики вашего сервера.

- `jira_search`: `{"jql":"project = APP ORDER BY updated DESC","limit":10,"cursor":""}`. Возвращает задачи и `next_cursor`; для следующего запроса передайте полученный cursor. Для Cloud используется новый `/rest/api/3/search/jql`, для Server/Data Center — `/rest/api/2/search`.
- `jira_issue`: `{"issue":"APP-123"}` — описание, статус, исполнитель, проект и ссылка. Atlassian Document Format преобразуется в текст.

### Confluence

`url`: адрес сайта, для Cloud можно указать адрес портала или адрес с `/wiki`, для Server/Data Center — полный базовый адрес с context path. `edition` и `auth_mode` настраиваются аналогично Jira.

- `confluence_search`: `{"cql":"type = page AND space = TEAM","limit":10,"offset":0}`. Возвращает найденный контент, фрагменты и `next_offset` (`-1` означает конец).
- `confluence_page`: `{"page_id":"12345"}` — текст страницы, заголовок, версия и ссылка. Чтение Cloud-страниц использует REST v2, поиск — CQL API; Server/Data Center — REST v1.

### Redmine: от имени пользователя по логину и паролю

По умолчанию `auth_mode: basic`: укажите URL сервера, **логин конкретного пользователя в username** и **его пароль в password**. Запросы выполняются через HTTP Basic Auth с правами этого пользователя, без заголовка подмены пользователя `X-Redmine-Switch-User`. На сервере Redmine должен быть включён REST API. При необходимости остаётся отдельный режим `auth_mode: api_key`: API-ключ задаётся в поле password и отправляется в `X-Redmine-API-Key`.

- `redmine_issues`: `{"filters":{"project_id":1,"status_id":"*"},"limit":20,"offset":0}`. Разрешённые фильтры: project_id, status_id, assigned_to_id, tracker_id, subject. Возвращает задачи и total_count. Для следующей страницы увеличьте offset; без status_id Redmine обычно возвращает только открытые задачи.
- `redmine_issue`: `{"issue_id":123}` — задача и до 100 записей журнала изменений.

### Bitrix24

Создайте входящий webhook с необходимыми правами чтения задач, а для лидов — CRM. В `url` укажите **только адрес портала**, например `https://company.bitrix24.ru`. Из webhook вида `/rest/42/TOKEN/` укажите `42` в username, а TOKEN — в password. Полный секретный URL нельзя помещать в обычное поле адреса.

- `bitrix24_tasks`: `{"group_id":0,"limit":20,"start":0}` — задачи доступных групп. group_id=0 не добавляет фильтр по группе. Для следующей страницы используйте next_start (`-1` — конец).
- `bitrix24_task`: `{"task_id":123}` — описание, статус, срок и ответственный задачи.
- `bitrix24_leads`: `{"limit":20,"start":0}` — базовые данные лидов без контактных реквизитов. Требует отдельного включения crm_enabled и соответствующих прав webhook.

В навыках поиска/списков limit ограничен диапазоном 1–50. Все девять навыков доступны в конструкторе агента и для CLI `skills test`; при вызове агентом требуется подтверждение. В разделе проверки источников можно запустить явный тест с приведённым JSON. Адаптеры не создают, не изменяют и не удаляют задачи/страницы/лиды. Bitrix24 вызывает фиксированные методы чтения через POST, остальные сервисы — через GET. Размер HTTP-ответа ограничен 2 MB, автоматические редиректы не выполняются. Тела ошибок сервисов с возможными секретами не выводятся.

Документация протоколов: [Jira search API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-search/), [Confluence CQL search](https://developer.atlassian.com/cloud/confluence/rest/v1/api-group-search/), [Redmine REST authentication](https://www.redmine.org/projects/redmine/wiki/Rest_api#Authentication), [Bitrix24 tasks](https://apidocs.bitrix24.com/api-reference/tasks/tasks-task-list.html). Реальные серверы без реквизитов пользователя не проверялись; запросы, авторизация, пагинация и ограничения покрыты mock-тестами.

## Запись задач Jira, Redmine и Bitrix24 с подтверждением

В конструкторе агента доступны шесть дополнительных навыков:

- `jira_create_issue`, `jira_update_issue`;
- `redmine_create_issue`, `redmine_update_issue`;
- `bitrix24_create_task`, `bitrix24_update_task`.

Они помечены как необратимые операции и требуют отдельного подтверждения **каждого вызова**, независимо от настройки confirmation_required агента. Перед записью платформа готовит одноразовый план: сервис, URL, действие, задача, предлагаемые поля, точные поля API и текущее состояние для изменений. План отображается в блоке подтверждения чата и в CLI. Изменение параметров модели или настроек подключения не подменяет подготовленный запрос. План нельзя использовать повторно.

Для изменения перед подтверждением выполняется чтение задачи; после подтверждения задача читается ещё раз. Если состояние отличается, запись отклоняется: нужны новый просмотр и подтверждение. Это дополнительная проверка конкурентных изменений, а не распределённая транзакция — между последним чтением и записью всё ещё возможны изменения другого клиента.

Без подтверждения, при отказе, истечении ожидания или отзыве сессии запрос записи не выполняется. Общие endpoints тестирования подключений/навыков не принимают запись: используйте чат или интерактивный CLI `skills test`. В Telegram/Mattermost/XMPP операции с подтверждением по-прежнему отклоняются. Все результаты попыток записи аудируются. Если связь оборвалась после отправки, результат может быть неизвестен; автоматического повторения нет — сначала проверьте внешний сервис. Дополнительная модель обработки результата не запускается после записи, чтобы её сбой не превращал успешное сохранение в повторную попытку.

### Jira

Создание:

```json
{"fields":{"project_key":"APP","issue_type_id":"10001","summary":"Новая задача","description":"Подробности","assignee_id":"ACCOUNT_ID"}}
```

Изменение:

```json
{"issue_key":"APP-123","fields":{"summary":"Новый заголовок","description":"Новое описание"}}
```

Допустимые поля обновления: summary, description, assignee_id, priority_id, due_date (`YYYY-MM-DD`, пусто — очистить), labels (массив меток). `assignee_id: null` снимает назначение; Cloud использует accountId, Server/Data Center — username. При создании обязательны project_key, issue_type_id, summary. ID типа задачи и исполнителей должны соответствовать вашей базе. В Cloud описание преобразуется в ADF, в Server остаётся текстом. Проект/тип существующей задачи и workflow-статус этим навыком не меняются. Дополнительные обязательные custom fields пока не поддерживаются; если они настроены, Jira может отклонить создание.

### Redmine

```json
{"fields":{"project_id":1,"subject":"Новая задача","description":"Подробности","assigned_to_id":5}}
```

```json
{"issue_id":123,"fields":{"subject":"Обновлённая тема","status_id":2,"notes":"Пояснение изменения"}}
```

При создании обязательны project_id и subject. Другие разрешённые поля: description, tracker_id, status_id, priority_id, assigned_to_id, due_date, start_date, done_ratio (0–100), notes. Даты — `YYYY-MM-DD`. Изменение проекта существующей задачи не поддерживается. Запись производится с настроенными логином/паролем пользователя (либо его API-ключом в отдельно выбранном режиме); права и допустимые статусы проверяет Redmine.

### Bitrix24

```json
{"fields":{"title":"Новая задача","responsible_id":42,"description":"Подробности","group_id":3}}
```

```json
{"task_id":123,"fields":{"title":"Новое название","deadline":"2026-12-01T18:00:00+03:00"}}
```

Разрешённые поля: title, description, responsible_id, group_id, deadline (ISO с часовым поясом или пусто), priority (0–2). Для создания обязательны title и responsible_id. Используются фиксированные методы `tasks.task.add`/`tasks.task.update` стандартного REST API с правами настроенного webhook. Запись CRM, удаление задач и изменение статуса Bitrix24 этим набором не реализованы.

CLI-пример (после настройки подключения в соответствующем пространстве):

```bash
superagent --user alice skills test jira_create_issue --input '{"fields":{"project_key":"APP","issue_type_id":"10001","summary":"Новая задача"}}'
```

Команда показывает план и спрашивает `[y/N]`; только `y` разрешает отправку. Идентификаторы в примерах условные. Реальные записи в ваши системы при разработке не выполнялись — проверки используют поддельные HTTP-ответы.

## Диспетчер задач, контроль зависших задач и подготовка релиза

В разделе «Агенты» нажмите **«Создать диспетчера задач»**, выберите вашу подключённую модель и сохраните агента `work_manager`. Репозиторный шаблон: `agents/work_manager.yaml`. Он объединяет три новых навыка, чтение почты и задач, а также создание задач Jira, Redmine и Bitrix24 с подтверждением. Входящие письма можно сначала получить через imap_read, затем передать выбранное письмо диспетчеру. Эти сценарии запускаются по запросу; фоновых рассылок и публикаций нет.

### task_dispatch

Готовит структурированное предложение из одного письма или сообщения, не отправляя HTTP-запросы и не создавая задачу. Модель агента помогает выбрать параметры, но неизвестные ID нужно уточнять, а не выдумывать.

```json
{"service":"jira","project":"APP","message":"Нужно подготовить отчёт к 2026-12-01","summary":"Подготовить отчёт","assignee":"","due_date":"","issue_type_id":"10001"}
```

service: jira/redmine/bitrix24. Для Jira project — ключ проекта, issue_type_id — ID типа задачи; для Redmine project — ID/идентификатор проекта; для Bitrix24 project — ID группы (можно оставить пустым), assignee — обязательный ID ответственного. В Jira assignee — accountId (Cloud) или имя пользователя (Server), в Redmine — ID пользователя. Пустой summary берётся из первой строки сообщения.

Результат `proposal` содержит имя create-навыка, его input, ready, missing_fields, кандидаты дат и saved=false. Найденные в тексте даты **не назначаются автоматически**. due_date задаётся явно: YYYY-MM-DD для Jira/Redmine, ISO с часовым поясом для Bitrix24. Для записи требуется отдельный вызов указанного create-навыка и отдельное подтверждение плана. Подтверждение работы диспетчера не является разрешением создать задачу.

### stalled_tasks

Читает открытые задачи одного проекта Jira или Redmine и выделяет причины:

- overdue — срок ранее даты отчёта;
- no_updates — последнее обновление было stale_days дней назад или раньше.

```json
{"service":"jira","project":"APP","stale_days":7,"as_of":"","limit":100}
```

as_of — ISO-время с часовым поясом, пустая строка использует текущий момент (Europe/Moscow для даты отчёта). stale_days: 1–365, limit: 1–200. В результате `stalled` есть список задач со ссылками и причинами, examined, truncated и unknown_update_time. Задачи с неизвестной датой обновления не объявляются зависшими по этому признаку. Просрочка определяется по календарной дате, задача со сроком сегодня ещё не просрочена.

Сервис читается постранично до limit. При truncated=true отчёт неполный; examined — число просмотренных задач, а не размер всего проекта. Никакие статусы, исполнители и сроки не меняются; отсутствие обновлений само по себе не доказывает блокировку.

### release_notes

Готовит Markdown-черновик из закрытых задач конкретной версии:

```json
{"service":"jira","project":"APP","release":"1.2.3","limit":100}
```

Для Jira release — точное имя или ID fixVersion; для Redmine — числовой fixed_version_id. Jira отбирается по statusCategory=Done, Redmine — по закрытым статусам. Результат `notes` содержит markdown, исходные задачи, examined, truncated, draft=true, published=false. Изменения группируются по типу задачи; каждый пункт содержит ссылку на источник. limit: 1–200; пустая или неполная выборка явно отмечается. Черновик можно перенести в Confluence вручную — навык не публикует страницу и не создаёт релиз во внешней системе.

Примеры запросов агенту: «Разбери это письмо и предложи задачу в проект APP», «Найди задачи APP без обновлений за 7 дней и просрочки», «Подготовь release notes Jira APP версии 1.2.3». Системы должны быть настроены в личном разделе подключений. Протоколы Jira/Redmine используются те же, что у существующих навыков чтения; реальные рабочие задачи в тестах не затрагиваются.

## Публикация release notes в Confluence

Добавлен отдельный навык `confluence_publish_release`. Черновик `release_notes` по-прежнему ничего не публикует; передайте его Markdown отдельному навыку публикации и подтвердите план. Новый шаблон work_manager уже включает чтение страниц и публикацию. Существующим агентам добавьте навык вручную.

Вход: `page_id`, `space_id`, `space_key`, `parent_id`, `title`, `markdown` — все строки; необязательные значения пустые. Для новой страницы Cloud задайте числовой space_id, для Server/Data Center — space_key. parent_id задаёт родительскую страницу в том же пространстве. При обновлении задайте page_id, title и markdown, оставив остальные поля пустыми. Обновление полностью заменяет заголовок и тело страницы.

Пример создания Cloud-страницы:

```json
{"page_id":"","space_id":"123","space_key":"","parent_id":"","title":"Release 1.2","markdown":"# Release 1.2\n\n- Исправлена ошибка APP-1"}
```

Перед подтверждением показываются сервер, пространство, страница, заголовок, полный Markdown, точное тело API и прежнее содержимое при обновлении. Публикация использует снимок подключения и одноразовое подтверждение. Отказ, отсутствие подтверждения или прямой тестовый API не выполняют запись. Версия страницы проверяется повторно после подтверждения; PUT использует следующий номер версии, а конфликт требует нового просмотра. Удаление страниц и перенос между пространствами не поддерживаются.

Markdown преобразуется в storage HTML локально. Сырой HTML и изображения не исполняются/не встраиваются; ссылки и структура release notes сохраняются. Cloud использует REST v2, Server/Data Center — REST v1. Нужны права внешнего пользователя на создание/изменение страниц. При неизвестном результате сетевого запроса автоматического повтора нет.

### Фото, голос и веб в чате

Кнопка фото прикрепляет до четырёх JPEG/PNG/WebP. Браузер уменьшает изображения
до 1536 пикселей и 300 КБ на фото, удаляя исходные метаданные. Фото отправляются
выбранному API вместе с сообщением: выберите модель с поддержкой изображений.
Они сохраняются в истории только текущего пользователя. Демо-модель фото не читает.

Микрофон включает голосовой ввод в текстовое поле через SpeechRecognition браузера.
Нужны HTTPS, разрешение на микрофон и поддерживаемый браузер. Распознавание может
использовать внешний сервис браузера; перед отправкой текст можно отредактировать.

Планета включает веб для отправляемых сообщений: `web_read` читает публичные HTML
и текстовые страницы; `web_search` доступен при настроенном Tavily/Brave/SearXNG.
В выключенном состоянии стандартные веб-навыки исключаются из доступных инструментов.
Чтение блокирует приватные/локальные IP, закрепляет разрешённый DNS-адрес при
подключении и заново проверяет перенаправления. Текст страниц считается недоверенным.

### Расписание

Раздел «Расписание» поддерживает разовый запуск, интервал, ежедневные и еженедельные
запуски с часовым поясом IANA (по умолчанию Europe/Moscow). Даты первого разового
запуска/интервала вводятся в часовом поясе браузера. Сервис должен работать; открытый
браузер не требуется. Пропущенные интервалы не накапливаются. При перезапуске
незавершённая задача помечается прерванной и не повторяется автоматически.

Расписания и результаты изолированы по пользователям, результат открывается как диалог.
Разрешение на чтение настроенных источников задаётся при создании расписания.
SSH, запись файлов и изменения во внешних системах не получают автоматического
подтверждения. Пауза и удаление расписания отключают будущие запуски; уже начатый
запуск продолжается. Можно создать до 20 расписаний на пользователя.

### Общий чат и подключаемые агенты

Новый диалог начинается как обычный чат с выбранной моделью. Выберите агента в
панели чата, чтобы поручить ему следующую задачу. Агент работает со своей моделью
и навыками, получая историю текущего диалога. Кнопка «Отключить» возвращает обычный
чат: переписка, фотографии и результаты навыков остаются в том же диалоге.
История хранится полностью; при превышении окна контекста выбранной модели API
может потребовать сократить диалог. Права предыдущего агента после отключения
не сохраняются. Подтверждения защищённых действий обязательны.

Прежние диалоги агентов доступны в истории. При отключении или смене агента такой
диалог копируется в общий чат; исходная история сохраняется. Общие диалоги находятся
в `data/conversations.db` внутри пользовательского пространства.

Веб-интерфейс получает события короткими запросами, чтобы доставка ответов и
карточек подтверждения не зависела от буферизации SSE промежуточным прокси.
SSE остаётся доступен для клиентов API. Сохранённые ответы можно открыть из истории.
